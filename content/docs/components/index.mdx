Pages on the ProTrainings site are composed from blocks. This section documents what a block is, the three classes blocks fall into, and the rules that decide which class a new block belongs to.

The organizing question is **who supplies the content**. That single axis predicts implementation cost more reliably than visual similarity does, and it is what the three classes below are named for.

<Callout type="info">
This page is a draft. The v1 inventory at the bottom is a proposal, not a commitment, and several decisions marked open below have downstream cost consequences.
</Callout>

## The three classes

| Class | Who supplies content | Who controls arrangement |
| --- | --- | --- |
| **Columns** | Editor composes | Editor, within fixed widths |
| **Brand Layouts** | Editor fills | Design |
| **Bound Sections** | The system | Design |

### Columns

A container block holding a single flat array of cells. Each cell is one block carrying its own `size` — `full`, `half`, `third`, `quarter`. There is no rows array, no columns array, and no nested Columns block. Rows are emergent: cells lay out left to right across a twelve-column grid and wrap when the next one doesn't fit.

Structurally this is the Payload website template's Content block with the `richText` field replaced by the block itself. `size` is a shared field spread into every cell-class block rather than a property of a wrapper, which is what keeps reordering flat — a cell can be dragged anywhere in the array, including across what renders as a row boundary.

**Columns is always margin-bound.** It lays out inside the content measure at every size, including `full`. Breaking the measure — edge-to-edge media, full-bleed color fields — is what Brand Layouts do and Columns does not. That is the boundary between the two classes: bleed, not width. A full-measure Rich Text block and a full-bleed hero are not the same output, so the two classes never produce the same result by different routes.

`full` is available per block type, not universally. Content-shaped blocks take it — Rich Text, Image / Media, CTA, Form. Card-shaped blocks do not: a full-measure Statistic Card or Course Card is a composition nobody needs the option to build. Because `size` is a shared field, the options array can differ per block, so this is enforced declaratively at the schema rather than through review.

Additional sizes are expected. `sixth` in particular unlocks asymmetric arrangements — `2/3 + 1/6 + 1/6` and its permutations — at the cost of one enum value, with every ordering available for free. Which sizes are actually needed is a brand decision and is deferred until brand direction returns.

#### Partial rows

Rows do not have to resolve to twelve. A lone `third` is a third-width block with negative space beside it, and that is a legitimate composition rather than an error state — it will also be the honest result for a number of source pages during migration.

Leftover space flows to the end of the row. Cells align to start; nothing centers, stretches, or redistributes to close the gap. There is no save-time validation on row totals and no auto-normalization of sizes. Both would intervene on intermediate states an editor is still composing, and normalization in particular edits intent in a way that can't be diagnosed from the admin.

If brand determines that lone partials are never acceptable, that is a rule enforced by not designing pages that way, not a schema constraint.

#### Stacking

A cell holds one block. That constraint produces the rule:

> **Columns place peers. Anything with internal hierarchy is a Brand Layout.**

The pressure this creates is absorbed in two places. The Rich Text block handles heading-plus-body in a single cell, which covers most stacking cases. Compositions with real internal hierarchy — a headline governing a set of images, for instance — are designed as Brand Layouts rather than assembled.

#### Blocks available in cells

- Rich Text
- Statistic Card
- Course Card
- Blog / Insight Card
- Poster (graphic or image with structured content beneath)
- Image / Media
- List (icon-paired items; the alternative to unordered lists in Lexical)
- CTA (poster-style, constrained to column width)
- Form *(pending the forms decision — see open decisions)*

### Brand Layouts

Full-section layouts where design owns the arrangement and the editor supplies content and selects media. The editor chooses the section, not the composition inside it.

These are the sections permitted to break the content measure. Edge-to-edge media, full-bleed color fields, and any arrangement with internal hierarchy live here rather than in Columns.

- Full-Width CTA (simple and rich-text-plus-media variants)
- Branded Layouts for 0, 1, 2, and 3 images
- Logo Rail

Hero treatments are not blocks. Four hero options are planned and they resolve as a page-level field, not as an entry in a blocks array.

### Bound Sections

Content the editor does not type. Two mechanisms sit under this class and they are not interchangeable.

**Query-bound** blocks take a filter and return many documents. The editor configures scope and variant; the content arrives from a collection. These carry populate logic, depth control, and a cache-invalidation story tied to the source collection.

- Reviews
- FAQs
- Course Grid
- Related Courses (slider)
- Video Course carousel

**Reference-bound** blocks take a pointer to one document and render that document's own blocks array. The general mechanism is a **Reusable Content** block backed by a `reusable-content` collection.

One block type covers every future "same content, many pages" case. *Three Easy Steps to Certification* is a document in that collection, not a schema — it is ProTrainings content rather than a structural pattern, and modeling it as its own block type would carry brand-specific weight into any future tenant.

<Callout type="warn">
These are not Payload **globals**. Payload globals are singletons — one per instance — and cannot be tenant-scoped without becoming a collection anyway. The term should not appear in this section.
</Callout>

## Rules that hold across all three

**Surfaces are owned by the section wrapper.** `data-surface` is set once at the section level and every nested cell adopts it. Cells cannot set their own surface. The surface treatment spans the full width of the section regardless of how the cells fill it — a lone third-width cell sits on a full-width background, with the negative space beside it carrying the same surface. Inset contrast comes from blocks that are themselves surface-bearing primitives — Statistic Card, Poster — never from arbitrary cell configuration. Two competing surface mechanisms produce checkerboard, and there is no editorial remedy for that once it exists.

**Height behavior is a component contract, not an editor setting.** Each block type declares fill or align-start once in its component definition. Card-type blocks fill; content-type blocks align to start; the grid is `align-items: stretch`. Extreme height deltas remain an editorial problem with an editorial remedy — different content, not a different toggle.

**Rich Text owns free-standing headings.** A block carries its own title field only when that title is structural to the data it represents: a Statistic Card's label, a Course Card's course name. Those are data fields, not headlines. Anything else that needs a heading in a cell uses Rich Text. Allowing both produces two typographic treatments for the same visual role.

**Heading levels are governed per field.** Lexical's heading feature is restricted at the field definition. Cells emit H2/H3 only; the fuller range is available in post body fields. On a replatform whose premise is SEO preservation, a broken heading hierarchy is a defect rather than a nit.

**Governance is the per-field block list.** Which blocks are available to which page model is expressed directly as the `blocks` array on each field. It is declarative, it lives with the schema, and it requires no permissions layer.

## Scope of this section

This inventory covers **composed pages** — the Pages collection and its blocks field.

Typed routes are out of scope here. Course Category and Course Detail are template × query and resolve from the Courses collection; they do not carry a blocks array. Posts are a separate layout with their own hero options and a sidebar of simple components.

Acceptance / Approvals is the known exception: a technical pillar page with hardcoded behavior. If it needs composable sections, they are appended as a single optional field with a restricted block list — bound sections and CTA only — rather than an open blocks array.

<Callout type="warn">
An open blocks array on a typed route converts it to a composed route with extra steps and invalidates the template × query estimate. If an escape hatch is needed, it is a fenced exception, not a general door.
</Callout>

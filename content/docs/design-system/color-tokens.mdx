This section covers the color token pipeline: what is authored by hand, what is derived, and what varies per brand.

<Callout type="warn" title="Primitive layer — only for testing until Brand produces a palette">
The prototype token object currently defines its own placeholder primitives inline. The architecture calls for a single shared CSS custom property file (OKLCH values) consumed by this pipeline. When the color palette is approved in the Brand workstream, the primitives here need to import from that canonical file rather than redeclare their own copy — otherwise two sources of truth can drift.
</Callout>

## Surfaces

A **surface** is a section-level ground an editor assigns to a block when composing a page. Every surface resolves the same set of token names, so a component references a name and never checks which surface it is in.

There are four roles. A role is a *position with a derivation rule*, not a set of values.

| Role | Ramp | Position | Extendable |
|---|---|---|---|
| **Base** | Brand neutral | Outermost step — lightest in light mode, darkest in dark | No |
| **Tint** | Any branded or brand-neutral | Lighter contrast from Base | Yes |
| **Shade** | Any branded or brand-neutral | Darker than Base | Yes |
| **Bright** | Any branded | High chroma | Yes |

Roles are defined by their **relationship to Base**, not by which ramp they draw from. Tint sits lighter, Shade sits darker, and Bright is the saturation role. Any of the three can extend from any branded or brand-neutral ramp — that is what makes the roster genuinely flexible rather than a fixed palette wearing role names.

The naming is literal rather than borrowed: a tint moves a hue toward white, a shade moves it toward black. Base is the neutral reference both are measured against.

**Base is the page ground everything else is defined against.** Its neutrality is structural, not chromatic — a warm cream Base is still Base. A brand whose page ground is cream or rich black defines that here rather than adding a surface to avoid white.

**Dark saturated grounds are Shade variants, not Bright.** Bright is the high-chroma-high-lightness role. A deep saturated plum is a Shade variant that happens to be chromatic, which keeps the name accurate and the polarity rule doing the work.

### Extension

Tint, Shade, and Bright are extendable. A variant supplies a different ramp or a different step in the same role — `brightCitron`, `shadeSand` — and runs through the same derivation, lands in the same token contract, and is verified by the same contrast harness. The roster grows; the contract does not.

Variants are named for their color rather than their role. This is a deliberate exception to role-based naming: chromatic peers have no structural hierarchy to encode, editors select them visually, and within a brand the color *is* the meaning. Role names themselves stay role-based.

**Base is singular.** It is the reference ground, and a reference cannot be plural.

How many surfaces a brand needs is a brand decision. The system guarantees that any surface resolves the full contract and clears contrast; it does not cap the roster. That is a matter of design discipline and discretion, and the constraint that keeps it usable is page models rather than architecture.

## Ramps

A ramp is a complete scale — `0` through `950` — authored per brand. Surfaces name a ramp and a ground step; every other token in the surface derives by stepping from it.

This is what keeps the primitive layer real. Each value a surface resolves is a named primitive, which means `--border` on Base is literally `neutral-200` and can be said out loud. It also gives the Rails LMS something to consume: the primitive file is the shared cross-consumer contract, and it only exists if primitives are named steps rather than computed one-offs.

Three requirements:

**Uniform keys.** Every ramp defines every step. Derivation is index arithmetic — `ground + 100`, `ground − 200` — so a ramp missing a step resolves to undefined silently. `0` is included on chromatic ramps as a near-white tint rather than omitted, to keep the keys identical.

**Monotonic, evenly spaced lightness.** Derivation assumes one step is a consistent perceptual distance. Hand-authored ramps drift, and then `card` reads invisible on one surface and dramatic on another. A test asserts lightness decreases monotonically and no adjacent gap exceeds a multiple of the median.

**Chroma tapers.** High chroma is not reachable at the extremes of lightness in OKLCH — it gets gamut-clipped. Ramps peak mid-scale and taper at both ends, or the `50` and `950` steps come back muddier than intended and clip inconsistently across hues.

Brand will supply individual colors rather than complete scales. Those are placed at the step where their lightness naturally falls and the ramp is generated outward from that anchor — the approved color stays exact at its step, and the rest is even by construction rather than hand-tuned across a dozen values per hue.

### What a brand supplies

A neutral ramp, a brand ramp, and any additional ramps its variants draw from. That is the entire per-brand surface.

## What is authored and what is derived

| Layer | Authored or derived | Owner |
|---|---|---|
| Ramps | Authored (anchored, interpolated) | Brand |
| Ground step per surface | Authored | Design |
| Remaining tokens per surface | Derived — offsets from the ground | System |
| Overrides on any surface | Authored, sparse | Design |

Resolution is governed by the ground's **lightness**, not its saturation. A light chromatic ground resolves like a light surface; a dark one resolves like a dark surface. Chroma governs which end of the ramp `primary` selects and how border alpha is set — not polarity.

**Cross-ramp pairing is the normal case.** A `shadeSand` ground drawn from a warm neutral ramp still takes its `primary` from the brand ramp. Selection must therefore be governed by the ground's lightness, never by an assumption that ground and accent share a ramp — variants break the moment those diverge.

**Rule of thumb:** interactive states brighten on dark grounds rather than darkening — the same direction the browser's default focus ring would move on an inverted page.

**At the ends of a ramp,** offsets have nowhere to go. On light grounds `card` offsets *darker* than the ground, with lift coming from elevation; on dark grounds it offsets lighter. Clamping instead would resolve `card` and `background` to the same value and make the container invisible.

Derivation is a default, not a constraint. Any surface may override any token explicitly; the derivation fills the rest.

## Token contract

Names align to shadcn/ui exactly, so components install without rewriting class names. TypeScript keys are camelCase; the generator emits the kebab-case CSS custom property.

| Token | Guarantees |
|---|---|
| `background` | Section ground |
| `foreground` | Default text — passes contrast against `background` |
| `card` / `cardFg` | Container ground for grouped content, and text on it |
| `muted` / `mutedFg` | De-emphasized region, and secondary/caption text |
| `border` | Dividers, card outlines |
| `primary` / `primaryFg` | Primary CTA fill, links, emphasis |
| `primaryHover` / `primaryActive` | Interactive states — resolved per surface, not derived by darkening a shared value |
| `secondary` / `secondaryFg` | Filled button for a second action — low-chroma step from the surface's own ground |
| `accent` / `accentFg` | Subtle interactive ground — ghost and outline hover, dropdown and command rows |
| `ring` | Visible-focus outline — set per surface, not inherited from Base |
| `success` / `successFg` | Positive state feedback |
| `warning` / `warningFg` | Caution state feedback |
| `elevationSm` / `elevationMd` | Shadow — surface-scoped, since a cast shadow is invisible on a dark ground |
| `input` | **Reserved.** Gated on the forms decision. |
| `destructive` / `destructiveFg` | **Reserved.** Gated on the forms decision. |

`card` and `muted` are distinct roles even where they resolve to similar values. `card` is a container for grouped content; `muted` is a de-emphasized region. Keep `card` a small delta from `background` — components inside a card still pull `border` and `mutedFg` from the parent surface, and a large delta breaks them. A large delta is a surface, and surfaces are declared at section level.

`secondary` and `muted` are also distinct, and for a sharper reason: `muted` is a region treatment with no interaction guarantee, while `secondary` is an interactive fill that must clear AA against its foreground. They may resolve close together on Base and diverge elsewhere.

Elevation is surface-scoped because its correct value depends on what is behind it — the same test that puts color here and leaves spacing, radii, type, and motion global. It branches on polarity rather than scaling: light grounds get a real shadow, dark grounds get none, with lift coming from the `card` delta instead. The CSS variable is named `--elevation-*` because `--shadow-*` is Tailwind's own namespace and self-reference would be circular.

`primaryHover`, `primaryActive`, `success`, `warning`, and the elevation pair are extensions beyond shadcn's set. Everything else matches its expected name.

## Popover — global, not per-surface

Popover, dialog, and tooltip content renders through a portal, appended outside the DOM subtree of whatever triggered it. That severs the cascade a surface wrapper depends on, so resolving popover to its ambient surface would require a `SurfaceContext` plus stamping `data-surface` onto portaled content — real engineering cost with no concrete need. Popover is one fixed global pair.

```ts
export const globalTokens = {
  popover: ramps.neutral[0],
  popoverFg: ramps.neutral[900],
};
```

## Component layer — how a token becomes a rendered color

No component branches on which surface it is in.

```
[data-surface="base"] { --primary: …; --primary-foreground: …; }   ← set per surface
        ↓
@theme inline { --color-primary: var(--primary); }                 ← Tailwind v4
        ↓
bg-primary, text-primary-foreground                                ← utility classes
        ↓
cva({ variants: { default: "bg-primary text-primary-foreground" }}) ← shadcn component
```

`@theme inline` is required. Without `inline`, Tailwind resolves the value at build time and bakes it into the utility, and the per-surface cascade does nothing.

The same `<Button>` renders correctly under any `data-surface` ancestor with no conditional logic.

## Dark mode

Dark mode is a second resolution of the same roster, not additional surfaces.

A surface is an editorial choice authored into content; dark mode is a reader preference resolved at view time. If dark surfaces were roster entries, switching modes would mean remapping every block's stored surface value at render — moving the second axis out of CSS and into render logic. Instead the generator emits each surface twice from one config entry, the second prefixed with `.dark`.

```css
[data-surface="tint"]       { --background: …light…; }
.dark [data-surface="tint"] { --background: …dark…;  }
```

Editors never see dark surfaces, the roster stays the same length, and the contrast harness picks up the second set automatically because it iterates the config rather than the selectors.

The mechanism is free. The design work is not: in dark mode Base is dark, so a dark Shade has little to differentiate against and a low-chroma Tint stops reading as distinct. Roles compress, which means the dark resolution is a set of decisions about how roles stay distinguishable rather than the same values inverted. That needs real ramps to answer.

Not implemented. ProTrainings is not shipping dark mode.

## Surface nesting

Surfaces are declared at section level only. Nested blocks have no surface field — instead they inherit their values from their parent block. Inheritance is structural rather than a rule, eliminating human error and minimizing editorial decisions.

Within-surface layering is handled by the `card` token, not by a nested surface. A card on a dark ground resolves a lifted dark value and light foreground through the same cascade — no wrapper, no context.

An `emphasis` toggle is reserved as an override for the case where a nested block legitimately needs a different ground. The preferred answer is to promote that block to its own top-level section, which is already legal and requires no mechanism. Enum rather than boolean, for extensibility.

<TypeTable type={{
  emphasis: {
    description: 'Reserved. Elevates a nested block to a bright ground. Prefer promoting the block to a section.',
    type: '"none" | "strong"',
    default: '"none"',
  },
}} />

If built, `emphasis` must re-scope the full token set, not only ground and foreground — otherwise a card inside an emphasized block inherits the parent surface's card values.

## Image and gradient grounds

Handled at the block level, not in the surface roster.

A block with an image background renders an overlay, blur, or fill behind its content, and that treatment *is* the surface the content sits on. The block declares a normal surface for its content; the image sits behind it. Tokens stay accountable and the contrast check still runs.

The same applies to gradients. A gradient behind a block whose content declares a surface is fine. A gradient *as* a surface is not, because there is no single background value to verify against.

## Verification

Every foreground/background pairing on every surface — including every variant, in both modes — is computed and asserted, failing the build on violation.

| Pairing | Threshold |
|---|---|
| `foreground` on `background` | 4.5:1 |
| `cardFg` on `card` | 4.5:1 |
| `mutedFg` on `muted` and on `card` | 4.5:1 |
| `primaryFg` on `primary`, `primaryHover`, `primaryActive` | 4.5:1 |
| `secondaryFg` on `secondary` | 4.5:1 |
| `successFg` on `success`, `warningFg` on `warning` | 4.5:1 |
| `ring` on `background` and on `primary` | 3:1 |
| `input` | 3:1 (reserved) |
| `border` | none — decorative dividers carry no requirement |

Contrast runs on the **gamut-mapped** value, not the authored one. High-chroma grounds fall outside sRGB and browsers clip inconsistently; testing the ideal value would pass a color the browser renders differently.

This is what per-surface explicit values buy. Contrast is checkable in the token file rather than discovered in design review, and it scales automatically as variants are added.

## Extension discipline

The primary constraint is page models: which surfaces a given block may use in a given template.

Token contract additions should address a functional need, not a visual preference.

- `success` and `warning` were added because real page content (For Business account-status messaging) describes states that need to render.
- `destructive` is named and deliberately unresolved, gated on the native-versus-HubSpot forms decision. If forms stay embedded, it may never need a value.

Surface variants are the pressure valve for visual variety. The token contract does not grow to accommodate a palette.

## Known gaps

- **Ramps** are placeholder values pending the Brand workstream. The system needs a neutral ramp and at least one brand ramp with enough range to clear contrast at both ends.
- **`input` and `destructive`** are reserved pending the forms decision.
- **A guaranteed chromatic surface** is undecided. If page models bind to a surface by name, unqualified `bright` needs to exist in every brand; if page models specify surfaces per block per brand, it does not.
- **Text over an image with no overlay** is out of contract. Not forbidden, but the system makes no guarantee there and legibility has been verified by eye rather than by the harness.
- **Primitive layer** is still self-contained placeholder values and needs to import from the canonical shared file before this leaves prototyping.
